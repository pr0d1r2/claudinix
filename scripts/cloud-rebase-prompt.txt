Rebase one pull request of this repository onto `@BASE@` in this Claude
Code cloud session: #@PR@ (@URL@), branch `@BRANCH@`. You run
unattended: nobody answers questions, so do not stop to ask.

1. Read AGENTS.md and follow it exactly; it overrides any skill's
   defaults. Run tools inside the dev shell: `nix-dev --command <cmd>`
   when nix-dev is on PATH, else `nix develop --command <cmd>`. If the
   SessionStart hook warned, do what it says first.
2. Fetch and rebase:
   `git fetch origin @BASE@ @BRANCH@`,
   `git checkout -B @BRANCH@ origin/@BRANCH@`,
   `git rebase origin/@BASE@`.
3. Resolve each conflict:
   - A generated file or block (README badges, the docs/INTEGRATION.md
     step table and counts, docs/THIRD-PARTY-NOTICES.md, anything between
     `<!-- BEGIN ... -->` and `<!-- END ... -->` markers): take either
     side, then re-write it in the dev shell with
     `claudinix-dev badges --write`, `claudinix-dev steps --write` or
     `claudinix-dev notices --write`, and stage the result in that same
     commit. Never merge generated lines by hand.
   - CHANGELOG.md, a spec table (rows such as `T12|...`) or any list
     both sides added to: keep both sides' lines, in order.
   - A spec id (`T`, `V`, `B` or `C` plus a number) that the pull request
     adds and `@BASE@` already has: give the pull request's row the
     next free id, the highest of that letter over every `SPEC*.md` plus 1,
     and change every citation of it in the files the pull request
     changes, in the same commit. Commit messages keep the old id; name
     the change in your report.
   - Any other spec, doc or code file: keep what both sides meant.
   - Resolve every conflict yourself. Only when the two sides mean
     opposite things and the pull request does not say which wins: run
     `git rebase --abort`, push nothing, and report the conflict.
4. Keep every commit and its message; change nothing beyond resolving
   conflicts. Never use --no-verify.
5. Run the gate over the rebased branch:
   `hk check --from-ref origin/@BASE@ --to-ref HEAD >gate.log 2>&1; echo rc=$?`
   in the dev shell. A command still running at 120 s moves to the
   background: wait for its completion notice and use its real exit
   status, not the 120 s return. Read gate.log only when rc is not 0;
   fix only what the rebase broke, never weaken a check. Do not commit
   gate.log.
6. Push to the same branch:
   `git push --force-with-lease origin HEAD:@BRANCH@`.
   Push to no other branch and open no new pull request. Do not merge
   anything; the owner reviews and merges.
7. CI, after the push:
   Watch CI on the pull request's head commit with your GitHub tools
   (its check runs, and the failed job's log), checking about once a
   minute, for up to 30 minutes a round.
   - Green (every check passed or was skipped): go on.
   - Red: read the failed job's log and find the cause. Fix what the
     rebase broke, run the gate again, push again with the same command
     and watch again. Stop after at most 3 red rounds and report the
     failing check and the log line that shows why.
   - A check cancelled before any step ran, or one that never starts,
     is GitHub's trouble, not your code: change nothing and report it.
   Never weaken a check or edit a test to get green.
8. End with a short report: the branch's old and new head, each conflict
   and how you resolved it (each renumbered id, old and new), the gate's
   rc, the CI result, and anything blocked.
